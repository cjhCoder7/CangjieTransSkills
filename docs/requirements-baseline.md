# 需求基线

## 1. 文档目的

本文档定义的是 **项目级需求基线**，不是某一个功能点的局部需求说明。

它的作用是为后续所有工作提供统一判断标准，回答以下问题：

- 当前阶段到底要先做什么；
- 哪些交付物是必须有的；
- Skill 与翻译验证应满足哪些最低要求；
- 哪些事情现在不能做或不值得先做；
- 什么时候可以从“小样本验证”进入“Telegram 工程推进”。

## 2. 基线定位

### 2.1 这份文档解决的问题

当前仓库已经有项目背景、资源索引和路线图，但还缺少一份“所有实现都必须对齐的下限要求”。

本基线文档的重点不是规定最终 Skill 目录长什么样，而是先明确：

- Skill 方案必须解决哪些核心问题；
- 翻译流程必须保留哪些证据；
- 验证结果如何判断是否能进入下一阶段。

### 2.2 这份文档不解决的问题

以下内容暂不在本文件中做最终定案：

- Skill 的最终目录结构与命名规范；
- 最终采用哪个模型供应商与推理配置；
- Swift 与第三语言的具体源仓库选择；
- 大规模自动化平台或完整 UI 系统设计。

这些问题需要在后续专项调研和实验中逐步收敛。

## 3. 项目级刚性目标

### 3.1 最终目标

项目最终应满足以下目标：

- 支持至少 **三种源语言到仓颉语言** 的转换验证；
- Telegram 相关交付至少覆盖：
  - `ArkTS / HarmonyOS` 场景；
  - `Swift / iOS` 场景；
- 第三种语言在 `Java` 或 `Python` 中择一完成验证；
- 提供可复现的转换过程轨迹；
- 具备单元测试与人工功能核查证据。

### 3.2 当前阶段目标

当前阶段的目标必须收敛在以下范围：

1. 建立项目文档基线与目录基线；
2. 明确 Skill 的最低结构要求与验证要求；
3. 完成 ArkTS 小样本验证所需的最小闭环设计；
4. 为后续 Telegram ArkTS 工程推进准备方法与标准；
5. 不直接进入完整 Telegram 全量翻译。

## 4. 范围基线

### 4.1 当前阶段必须纳入范围

- Cangjie / HarmonyOS 官方资料整理；
- 官方 Skill 仓库结构调研；
- 项目自建 Skill 的最小单元定义；
- ArkTS 小样本筛选与验证；
- 翻译、构建、运行、记录的最小流程设计；
- 项目文档、目录、脚本与产物沉淀规范。

### 4.2 当前阶段明确不纳入范围

- 全量 Telegram 一步到位翻译；
- 未经验证直接构建庞大的自动化 Agent 平台；
- 在样本未跑通前同时铺开 Swift 与第三语言；
- 将敏感密钥或受限资料直接提交到仓库。

## 5. 交付物基线

### 5.1 当前阶段必须交付

当前阶段至少应交付以下内容：

- 项目级说明文档；
- 需求基线与评测标准；
- 资源索引与目录约定；
- Skill 最小单元模板或等价说明；
- ArkTS 小样本候选列表；
- 小样本验证记录模板；
- 产物与轨迹沉淀路径说明。

### 5.2 后续阶段必须交付

随着项目推进，至少应逐步补齐：

- 翻译输入与输出示例；
- 构建 / 测试 / 运行命令与结果；
- 问题清单、复盘结论与回写记录；
- Telegram ArkTS 分模块推进方案；
- Swift 与第三语言的补齐方案与验证记录。

## 6. Skill 需求基线

> 结论先行：Skill 的“最终形状”可以后定，但 Skill 的“最低结构要求”必须先定，否则会直接影响检索命中率、Agent 选用正确上下文的能力，以及后续验证与维护成本。

### 6.1 Skill 方案必须解决的问题

无论最终采用什么目录结构，Skill 方案都必须能解决以下问题：

1. **可定位**：让 Agent 知道什么时候该用这个 Skill；
2. **可检索**：当 Skill 本身不完整时，知道去哪里补知识；
3. **可操作**：不仅讲概念，还能指导具体实现与验证；
4. **可验证**：Skill 中的知识点能映射到样本、代码或实验；
5. **可维护**：后续更新某一类组件或规则时，不会牵一发而动全身；
6. **可追溯**：能回到原始文档、样例或官方来源。

### 6.2 Skill 最低内容要求

任何一个进入项目的 Skill 单元，至少应具备以下信息：

- `名称 / 标识`
- `适用领域`
  - 例如：UI 组件、页面路由、构建流程、系统能力、网络接口、AI 接口
- `适用场景 / 触发条件`
  - 说明 Agent 在什么情况下应优先调用该 Skill
- `核心知识`
  - 该场景下必须掌握的规则、约束、接口、组件行为或映射关系
- `来源与版本信息`
  - 文档链接、样例来源、访问时间、版本标识
- `示例`
  - 至少一个正向示例；如条件允许，补充一个反例或常见坑
- `验证方式`
  - 如何验证该 Skill 内容是否有效，例如编译、运行、页面观察、接口调用、单测
- `缺口与降级策略`
  - 如果 Skill 覆盖不完整，Agent 应如何继续处理

### 6.3 Skill 结构设计约束

后续设计 Skill 结构时，至少应满足以下约束：

- **按问题域切分，而不是按文档原始章节机械切分**；
- **单个 Skill 单元聚焦单一主题**，避免过大；
- **允许与检索工具联动**，而不是把所有原文硬塞进 Skill；
- **支持后续插入样例、坑位、版本差异与补充脚本**；
- **尽量让 Skill 内容可被评测**，而不是只保留描述性文本。

## 7. 翻译流程需求基线

### 7.1 最小流程要求

任何翻译实验，至少应保留下列阶段信息：

1. 输入来源；
2. 使用的 Skill / 检索资料；
3. 翻译步骤或关键中间决策；
4. 输出代码；
5. 构建 / 测试 / 运行结果；
6. 问题与修正记录；
7. 最终结论。

### 7.2 翻译产物最低要求

任何声称“已完成翻译”的结果，至少应满足以下一项：

- 成功编译；
- 通过约定的最小单元测试；
- 在模拟器 / 真机上展示目标页面或目标功能；
- 若失败，必须给出可复现失败条件与原因分析。

### 7.3 轨迹记录最低要求

后续所有关键实验都应尽量记录：

- 源文件 / 源片段；
- 目标文件 / 目标片段；
- 使用到的 Skill；
- 关键提示词、规则或脚本；
- 构建命令；
- 运行结果；
- 修复轮次；
- 最终状态。

## 8. 样本验证需求基线

### 8.1 样本选择要求

作为第一阶段验证样本，优先选择：

- 功能单一；
- 依赖较少；
- 组件使用清晰；
- 容易在 DevEco / 模拟器中快速验证；
- 能代表一类典型 ArkTS 开发问题。

### 8.2 当前不推荐的样本

当前阶段不推荐直接选择：

- 过度复杂的多页面应用；
- 强依赖网络、账号体系或大型后端的样本；
- 即使翻译成功也难以快速验证的样本。

### 8.3 样本验证的输出要求

每个样本验证至少应留下：

- 样本来源；
- 样本目标功能；
- 翻译范围；
- 验证方法；
- 结果状态；
- 发现的问题；
- 对 Skill 的反馈。

## 9. 工程与文档非功能基线

### 9.1 可追溯性

- 重要结论必须能追溯到来源文档、样例、代码或实验；
- 外部仓库必须记录来源、时间、版本；
- 实验结果应尽量沉淀到文档或产物目录。

### 9.2 可复现性

- 脚本输入输出要明确；
- 关键命令可重复执行；
- 重要实验至少记录环境与工具版本。

### 9.3 安全性

- 不得把明文密钥写入仓库；
- 不得在公共文档中扩散受限凭据；
- 需要内测权限的资源应注明访问前提。

### 9.4 可维护性

- 文档结构与目录结构要能支持后续迭代；
- Skill、样本、产物与外部代码应分目录管理；
- 方案变更要回写到协作文档。

## 10. 阶段推进闸门

### 10.1 进入 Skill 结构设计阶段前

至少应具备：

- 文档基线已经建立；
- 资源索引可用；
- 需求基线与评测标准已定出第一版。

### 10.2 进入 ArkTS 小样本验证前

至少应具备：

- 一个明确的 Skill 最小单元模板；
- 一套样本筛选标准；
- 一套评测口径；
- 至少一个可复用的验证记录模板。

### 10.3 进入 Telegram ArkTS 工程推进前

至少应具备：

- 至少一个 ArkTS 小样本完成完整验证闭环；
- 能明确说明 Skill 对翻译结果起到了什么作用；
- 已形成第一版问题模式与修复策略总结。

## 11. 当前待决策事项

以下内容仍需要专项调研后再定：

- Skill 的最终目录与文件格式；
- 是否直接兼容官方 `.opencode/skills/` 结构；
- 检索工具的接入方式与脚本边界；
- 轨迹记录的统一格式；
- 阶段性评分阈值是否要进一步量化。
