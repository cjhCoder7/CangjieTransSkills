# ArkTS 主线程 UI 更新边界：原始材料

## 1. 场景背景

在 ArkTS 声明式 UI 中，页面上的 `@State`、`@Link`、`@Prop`、`@StorageLink`、`AppStorage` 以及和 `LazyForEach` 绑定的数据源，本质上都属于 UI 线程可见状态。

当页面需要处理网络返回、消息解码、列表增量合并、磁盘读取、图片元数据探测等耗时任务时，不能直接在 UI 主线程做完整计算，否则会导致掉帧、滚动卡顿、输入延迟和动画抖动。

因此，一个典型的 ArkTS 工程会把工作拆成两段：

1. 后台线程或 taskpool 负责耗时计算，例如消息反序列化、diff 计算、列表批处理、富媒体尺寸分析；
2. 主线程只负责接收已经准备好的最小变更结果，并把这些结果提交给页面状态或 UI 绑定数据源。

## 2. 核心原则

### 2.1 计算与提交分离

- 后台线程负责计算，不直接碰 `@State`；
- 主线程负责提交，不在提交阶段再次做重计算；
- UI 只消费“已经整理好的变更结果”，而不是消费原始高频事件流。

### 2.2 UI 绑定状态只能在主线程提交

以下对象或状态，不应在后台线程直接读写：

- 页面组件中的 `@State` 字段；
- 通过 `@StorageLink` 绑定到全局存储的字段；
- 与 `LazyForEach`、`Repeat`、`List`、`Grid` 直接绑定的数据源监听器；
- 会立即触发组件重建、布局测量、节点创建或动画的可观察状态。

后台线程如果拿到了这些对象的引用，也不应直接修改，因为这会让状态所有权与线程归属变得混乱。

### 2.3 后台线程只输出最小变更包

对聊天、通知流、联系人变化这类高频场景，更好的做法不是把整份数据重新抛回主线程，而是在后台线程完成：

- 原始事件归并；
- 重复事件折叠；
- 列表增量 diff；
- 批处理窗口聚合；
- 错误分类与可重试标记。

然后只把最小变更包投递给主线程，例如：

- 新增了哪些索引；
- 删除了哪些索引；
- 哪些消息需要局部重绘；
- 哪个锚点需要保持稳定；
- 当前是否允许触发 `notifyDataReload`。

## 3. 典型 ArkTS 组织方式

### 3.1 taskpool 负责耗时计算

ArkTS 里常见的方式是把耗时工作交给 `taskpool` 或后台任务机制处理，例如：

- 拉取网络消息后，在后台做消息体解析；
- 对本地缓存和服务端回包做合并；
- 为长列表计算增量变更集；
- 对图片、视频消息做尺寸和占位信息预处理。

taskpool 阶段的输入应该是纯数据，不应该把页面组件实例直接传进去。

### 3.2 主线程负责状态提交

后台任务完成后，页面层或中间协调器在主线程完成如下动作：

- 更新页面级 Store；
- 更新和 UI 直接绑定的投影状态；
- 调用数据源的 `notifyDataAdd`、`notifyDataDelete`、`notifyDataChange`、`notifyDataReload`；
- 在必要时触发动画、滚动锚点修正和占位图切换。

主线程阶段应尽量短，只做提交，不做二次扫描全量列表。

### 3.3 不能让后台线程直接持有页面生命周期对象

页面被销毁、切后台、路由离开或 Ability 生命周期变化时，后台任务可能还在运行。如果后台任务持有页面对象并试图直接回写状态，就会出现：

- 页面已销毁但仍收到回调；
- UI 节点已释放但后台还在尝试更新；
- 跨页面状态被过期任务覆盖；
- 取消订阅、取消任务和资源释放不成对。

因此需要一个中间协调器，它负责：

- 判断页面是否还活着；
- 判断这次结果是否仍然是最新版本；
- 判断是否允许把结果提交给主线程；
- 在页面离开时统一取消订阅和失效旧任务。

## 4. 聊天与高频消息场景的特殊要求

聊天场景不是普通设置页。它会同时面对：

- WebSocket 或长连接高频推送；
- 本地缓存与远端回包竞态；
- 用户正在滚动时的新消息插入；
- 历史分页和最新消息同时到达；
- 富媒体消息导致的二次布局与尺寸变更。

因此，主线程 UI 边界不仅是“线程安全”问题，还是“拓扑分层”问题：

- 上游响应式流负责接收原始事件；
- 中游增量合并器负责后台生成批处理结果；
- 下游虚拟化列表只在主线程消费已经整理好的窗口投影；
- 页面组件只绑定最终投影，不直接绑定原始消息流。

## 5. 常见错误

### 5.1 在后台线程直接改 `@State`

这种写法最危险。即使短期不崩，也会让调试变得困难，因为页面刷新、生命周期和线程归属都失去确定性。

### 5.2 每次结果都全量 `notifyDataReload`

如果后台线程每处理一批消息，就让主线程全量重载列表，会造成：

- 主线程节点重建太多；
- 滚动锚点不稳定；
- 富媒体重复解码；
- 页面在高频消息时出现持续掉帧。

### 5.3 后台结果不做版本校验

如果用户已经离开页面，或者已经触发了更新的一轮请求，旧任务结果仍然提交到主线程，就会污染最新状态。

### 5.4 页面组件直接承担调度职责

如果把任务取消、状态合并、主线程派发、列表数据源通知、错误分类都写在页面组件里，页面会很快失控。更合理的方式是把这些职责收敛到协调器、Store 或 Presenter 层。

## 6. 对仓颉侧迁移的启发

将这类 ArkTS 模式迁移到仓颉时，重点不应放在“哪个 API 名字相同”，而应放在以下问题：

- 后台任务由谁持有；
- 主线程提交点在哪里；
- UI 绑定状态由谁拥有；
- 页面离开后谁负责取消旧任务；
- 列表数据源通知是否在主线程统一出口发出；
- 是否把原始事件流转换为最小变更包之后再进入 UI。

如果这些约束不先定好，即使生成的代码能编译，最终也很可能在高频消息、页面切换和生命周期抖动下失效。
