## Boundary Summary

- The prototype stays inside the existing sample package.
- `TelegramAppShell` itself may consume only:
  - `TelegramSessionListPage`
  - `TelegramChatDetailPage`
  - `TelegramPageRouter` state
- One same-package wiring helper may assemble the existing lower-layer objects required to produce those page instances:
  - `TelegramSessionListController`
  - `MainContextDatasetRefreshBridge`
- That wiring helper is the only allowed wiring exception in this slice and exists only to lift the shell onto the page/router consume layer.
- The prototype must not introduce route generalization, visual redesign, or cross-sample shared dependency.

## Current Consume Contract

- Initial shell state shall resolve to `TelegramSessionListPage`.
- `TelegramAppShell` shall not directly own or construct controller/bridge internals.
- The shell shall expose a list-loading entry that delegates to the existing `TelegramSessionListPage`.
- The shell shall expose a list-to-detail consume path that delegates to the existing router plus `TelegramChatDetailPage`.
- Once detail is active, the same-package shell may expose the active thread projection as the current conversation's real message list; this does not authorize wider UI redesign or generic thread/view abstraction.
- The shell may expose a targeted refresh entry only by delegating to the existing `TelegramSessionListPage.refreshConversation(peerId, limit)`.
- When the shell is already on `TelegramChatDetailPage`, opening another visible conversation shall reuse the active detail route instead of pushing a second detail entry.
- After backing from a retargeted detail route, the next list-to-detail navigation shall reuse the bounded detail slot and keep route history at `2` instead of inflating to `3`.
- After backing from detail to the session-list route, `currentDetailTitle()`, `currentDetailPeerLabel()`, and `currentDetailBody()` must clear instead of leaking the stale route-owned conversation.
- After backing from detail to the session-list route, a later shell-level `refreshConversation(peerId, limit)` must keep `TelegramSessionListPage` as the current route, keep detail getters empty, keep bounded history at `2`, refresh only the target summary, and leave non-target summaries untouched.
- After that list-route refresh has updated a visible target conversation, reopening that refreshed summary must return the shell to `TelegramChatDetailPage`, keep bounded history at `2`, bind detail title / peer label / placeholder body to the reopened target conversation, preserve the refreshed target summary on the list surface, and keep non-target summaries untouched.
- When refresh runs while the shell is already on a detail route for the target conversation, the current route, detail title, peer label, and placeholder body must remain pinned to that same route-owned target while the target summary is refreshed in place on the list surface.
- After that active-detail target refresh has completed, directly retargeting to another visible conversation must keep `TelegramChatDetailPage` active, keep bounded history at `2`, switch detail title / peer label / placeholder body to the new target conversation, preserve the refreshed original target summary on the list surface, keep the other visible summary unpolluted, and avoid any extra service-history pull beyond the refresh itself.
- After that active-detail target refresh is followed by `backFromDetail()`, the shell must return to `TelegramSessionListPage`, clear detail getters, preserve the refreshed target summary on the list surface, and keep bounded history at `2`.
- After that active-detail refresh-retarget sequence is followed by `backFromDetail()`, the shell must return to `TelegramSessionListPage`, clear detail getters, preserve the original refreshed target summary on the list surface, keep the retargeted visible summary untouched, and keep bounded history at `2`.
- Reopening the original refreshed target after that active-detail refresh-retarget-back sequence must return the shell to `TelegramChatDetailPage`, keep bounded history at `2`, rebind detail title / peer label / placeholder body to the original refreshed target, preserve the refreshed target summary, and keep non-target summaries untouched.
- After that original refreshed target has been reopened, a second `backFromDetail()` must again return the shell to `TelegramSessionListPage`, clear detail getters, preserve the original refreshed target summary and `messageCount` on the list surface, keep bounded history at `2`, and leave the other visible summary untouched.
- Reopening the other visible conversation after that second back must return the shell to `TelegramChatDetailPage`, keep bounded history at `2`, rebind detail title / peer label / placeholder body to the other visible conversation, preserve the original refreshed target summary and `messageCount` on the list surface, keep the other visible summary unpolluted before and after the final reopen, and avoid any extra service-history pull beyond the refresh itself.
- Reopening that same refreshed target after the active-detail refresh/back sequence must return the shell to `TelegramChatDetailPage`, keep bounded history at `2`, rebind detail title / peer label / placeholder body to the same refreshed target, preserve the refreshed target summary, and keep non-target summaries untouched.

- After that refreshed target has survived one reopen-retarget-back round trip, backing again and reopening another visible conversation must still restore `TelegramChatDetailPage`, keep bounded history at `2`, switch detail title / peer label / placeholder body to the newly reopened visible conversation, preserve the refreshed original target summary on the list surface, and keep the other visible summary untouched.
- `TelegramAppShell.sendMessageToActiveConversation(text)` may consume only the active detail route's same-peer send path and must not widen into a route-independent or generic send API.
- After `sendMessageToActiveConversation(text)` runs while the shell is already on `TelegramChatDetailPage`, the current route must remain `TelegramChatDetailPage`, bounded history must remain `2`, and `currentDetailTitle()`, `currentDetailPeerLabel()`, and `currentDetailBody()` must continue exposing the same route-owned detail placeholder contract.
