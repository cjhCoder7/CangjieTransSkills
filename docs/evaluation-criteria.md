# 评测标准

## 1. 文档目的

本文档用于统一项目中的“完成判断”和“质量判断”。

它服务于四类对象：

- 文档基线；
- Skill 单元；
- ArkTS / Swift / 第三语言翻译样本；
- 阶段里程碑与最终交付物。

## 2. 评测原则

### 2.1 先过闸门，再谈评分

任何交付物都应先通过基础闸门，再进行质量评分。闸门失败时，不应因某些局部表现良好而判定整体通过。

### 2.2 优先可验证证据

评分优先依据以下证据：

- 源代码或文档；
- 构建结果；
- 测试结果；
- 运行结果；
- 复现实验记录；
- 来源与版本记录。

### 2.3 优先可追溯与可复现

如果一个结果“看起来对”，但没有来源、过程和验证记录，应按低分处理，不能视为可靠成果。

## 3. 基础闸门（Hard Gates）

以下闸门适用于大多数交付物，未通过任一项时，不进入高分评价：

### 3.1 通用闸门

- 已记录输入来源；
- 已记录当前任务目标；
- 已记录关键过程或关键决策；
- 未在仓库中引入明文密钥；
- 输出位置清晰，其他成员可定位。

### 3.2 代码 / 翻译产物额外闸门

- 已记录源片段与目标片段的对应关系；
- 已记录使用的 Skill、检索来源或规则；
- 已进行至少一种验证：编译、测试、运行或失败复现；
- 若失败，已给出失败原因与下一步处理建议。

### 3.3 Skill 单元额外闸门

- 已标注来源；
- 已说明适用场景；
- 已说明验证方式；
- 已说明覆盖边界或已知缺口。

## 4. Skill 评测标准

Skill 单元建议按 100 分评估，推荐维度如下：

### 4.1 结构完整性（20 分）

评估点：

- 是否具备名称、适用领域、触发条件；
- 是否具备来源、版本或访问时间；
- 是否具备验证方式与缺口说明。

### 4.2 检索与触发清晰度（20 分）

评估点：

- Agent 是否容易判断何时使用；
- 场景边界是否明确；
- 是否能与检索工具或补充资料顺畅衔接。

### 4.3 操作性（20 分）

评估点：

- 是否能指导具体实现；
- 是否提供组件、接口、规则或步骤级信息；
- 是否能直接服务于代码翻译或问题修复。

### 4.4 示例质量（15 分）

评估点：

- 是否有正向示例；
- 示例是否贴近真实任务；
- 是否覆盖常见坑、反例或限制条件。

### 4.5 可维护性（10 分）

评估点：

- 单元粒度是否合适；
- 是否容易更新；
- 是否避免和其他 Skill 高度重复或强耦合。

### 4.6 可验证性（15 分）

评估点：

- 是否能映射到样本、代码或实验；
- 是否能通过编译、运行、页面观察或测试来验证；
- 结论是否有回写通道。

### 4.7 评分解释

- `90-100`：可直接作为高价值 Skill 使用；
- `75-89`：可进入样本验证，但仍建议补齐边界或示例；
- `60-74`：只能作为参考草稿，不应独立支撑关键翻译任务；
- `<60`：结构或内容明显不足，需要重写或拆分。

## 5. 翻译样本评测标准

翻译样本建议按 100 分评估，推荐维度如下：

### 5.1 语义保真度（20 分）

评估点：

- 目标代码是否保留了源代码的关键行为；
- 组件关系、状态逻辑、接口调用是否被正确迁移；
- 是否存在明显语义偏差。

### 5.2 编译可行性（20 分）

评估点：

- 是否能编译；
- 若不能编译，错误是否局部且可修复；
- 编译问题是否被分类记录。

### 5.3 运行正确性（20 分）

评估点：

- 是否能在模拟器 / 真机中运行到目标页面或功能；
- UI、交互、路由、接口行为是否基本正确；
- 是否存在阻断性运行错误。

### 5.4 工程可维护性（10 分）

评估点：

- 代码是否具有基本可读性；
- 结构是否符合目标语言与目标平台习惯；
- 是否过度依赖人工一次性补丁。

### 5.5 Skill 使用有效性（10 分）

评估点：

- Skill 是否确实帮助解决了翻译问题；
- 是否能说明某个 Skill 对结果的正向贡献；
- 是否识别出 Skill 的空白点与改进方向。

### 5.6 轨迹与证据完整性（20 分）

评估点：

- 是否记录了输入、输出、关键步骤、命令、日志与问题；
- 是否能复现主要过程；
- 是否能回溯到来源与版本。

### 5.7 评分解释

- `85-100`：样本闭环已具备较强说服力，可作为下一阶段依据；
- `70-84`：具备验证价值，但仍需补齐编译、运行或证据链；
- `50-69`：只能说明方法可能可行，不能支撑阶段推进；
- `<50`：实验质量不足，应先重做基线与记录。

## 6. 阶段推进评测口径

### 6.1 Phase 0：文档与工程基线

通过条件：

- 文档入口完整；
- 目录职责清晰；
- 需求基线与评测标准存在；
- 安全与外部资源约定明确。

### 6.2 Phase 1：Skill 结构与文档抽取规范

建议通过条件：

- 至少有一个 Skill 最小单元模板；
- 至少有若干代表性 Skill 单元样例；
- Skill 平均评分建议达到 `75+`；
- 能说明如何从文档进入 Skill，再进入验证。

### 6.3 Phase 2：ArkTS 小样本验证

建议通过条件：

- 至少一个样本通过基础闸门；
- 至少一个样本总分建议达到 `80+`；
- 编译 / 运行 / 问题记录三者至少具备其中两类有效证据；
- 能指出 Skill 对样本结果的直接影响。

### 6.4 Phase 3：Telegram ArkTS 推进

建议通过条件：

- 已形成模块级推进方案；
- 已在至少一个代表性模块上完成闭环验证；
- 已有成体系的问题分类与修复策略；
- 样本阶段的评测口径可平移到真实工程。

### 6.5 Phase 4：多语言补齐与最终验收

建议通过条件：

- 三种源语言均有明确验证结果；
- Telegram 相关关键场景有可复现证据；
- 单测与人工功能核查证据齐备；
- 轨迹信息完整，能支撑验收与项目复盘。

## 7. 最终验收建议口径

项目最终验收建议至少检查以下清单：

- 是否达到三种源语言转换要求；
- 是否完成 Telegram 相关场景验证；
- 是否有完整代码或可复现产物；
- 是否有单元测试证据；
- 是否有人工功能核查证据；
- 是否有完整轨迹信息；
- 是否能说明 Skill 在整个流程中的作用与局限。

## 8. 当前仍待细化的评测项

以下内容在后续研究中建议进一步量化：

- 不同类型 Skill 的差异化评分权重；
- UI 类与系统能力类样本的不同验收口径；
- Swift、ArkTS、Java/Python 三类源语言的独立评分细则；
- 轨迹信息的统一字段模板；
- 是否引入更正式的分级标签（如通过 / 有条件通过 / 不通过）。
