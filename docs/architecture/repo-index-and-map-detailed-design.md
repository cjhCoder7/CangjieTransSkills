# Repo Index 与 Repo Map 详细设计

## 1. 文档目的

本文是 `docs/architecture/repo-scale-translation-stack-design.md` 的子设计文档之一，专门细化仓库级翻译栈中的数据层与地图层。

本文重点回答以下问题：

1. `Repo Index` 应如何组织为可查询、可增量更新、可人工核查的事实底座；
2. `Repo Map` 应如何从 `Repo Index` 投影出来，以同时服务脚本与大模型；
3. 数据层应如何支持后续的 `Translation Unit` 切分、依赖闭包计算、错误驱动检索与失败回溯；
4. 如何定义当前阶段的数据质量指标与人工 spot check 口径。

本文只覆盖数据抽取、存储、投影、查询和质量控制，不覆盖翻译流水线的 Agent 编排细节。

---

## 2. 设计定位

### 2.1 Repo Index 的职责边界

`Repo Index` 的职责是把源仓库从“文件集合”变成“可计算的结构事实集合”。

它必须服务以下五类行为：

1. 为 `Translation Unit` 提供强依赖与弱依赖的候选集合；
2. 为 `Review` 提供状态、线程、互操作和生命周期风险的事实依据；
3. 为 `Verify` 提供验证锚点、模块角色和功能路径线索；
4. 为 `Repair` 提供错误驱动补拉上下文的查询入口；
5. 为 `Pattern Memory` 提供失败归因所需的源事实快照。

### 2.2 Repo Map 的职责边界

`Repo Map` 的职责不是“仓库摘要”，而是“面向翻译任务的结构压缩结果”。

它必须服务两类消费者：

- **脚本侧消费者**：需要结构化、可过滤、可预算控制、可增量更新；
- **模型侧消费者**：需要低 token、高密度、快速理解模块角色与关键边界。

因此，Repo Map 必须明确区分：

- 哪些信息是脚本要查的；
- 哪些信息是模型要看的；
- 哪些信息属于首轮上下文；
- 哪些信息属于错误触发后再补拉的上下文。

---

## 3. Repo Index 详细数据模型

## 3.1 总体结构

建议采用“快照表 + 主实体表 + 关系表 + 风险标记表 + 验证提示表”的五层组织方式。

```text
repository_snapshot
    ├── source_file
    ├── symbol
    ├── symbol_signature
    ├── import_edge / export_edge / call_edge / inheritance_edge
    ├── state_edge / thread_boundary_marker / interop_boundary_marker / ui_binding_marker
    └── verification_anchor / diagnostic_hint
```

这种设计的优点是：

- 便于增量更新；
- 便于区分“客观事实”和“启发式推断”；
- 便于把风险标签和验证标签作为横切关注点叠加到任何文件或符号上。

---

## 3.2 快照层

### 3.2.1 `repository_snapshot`

建议把一次完整或增量索引视为一个可追溯快照。

建议字段分组如下：

- **来源信息**：源仓库地址、分支、commit、拉取日期；
- **索引环境**：解析器版本、规则包版本、生成时间、运行机器标识；
- **构建方式**：全量 / 增量、触发原因、关联任务编号；
- **质量信息**：总文件数、解析成功数、低置信度结果比例、失败文件清单位置；
- **备注信息**：是否包含私有补丁、是否人为修正过索引结果。

### 3.2.2 快照设计原则

- 同一轮翻译与验证应只绑定一个快照；
- 若快照变更，则失败回溯必须说明前后差异；
- 若因权限或语法不兼容导致部分文件无法解析，必须在快照层明确标记，而不能静默忽略。

---

## 3.3 文件层

### 3.3.1 `source_file`

建议文件层承担“仓库定位、模块归类、解析结果汇总”的职责。

建议字段分组如下：

- **路径信息**：相对路径、模块路径、目录深度、文件名；
- **基础属性**：语言、大小、哈希、修改时间；
- **解析属性**：解析状态、解析耗时、解析置信度、是否命中特殊补丁；
- **架构属性**：架构角色、文件职责、模块边界、是否入口文件；
- **工程属性**：是否测试文件、是否样例文件、是否生成文件、是否资源配置文件；
- **风险属性**：是否高风险边界文件、风险标签集合；
- **验证属性**：推荐验证方式、推荐关联样本或页面入口。

### 3.3.2 文件职责标签建议

建议至少定义以下职责标签，以便后续 TU 自动切分时可直接利用：

- `page`
- `component`
- `viewmodel`
- `state`
- `service`
- `repository`
- `model`
- `router`
- `reactive`
- `interop`
- `bridge`
- `storage`
- `config`
- `test`

### 3.3.3 文件级质量要求

文件层至少应保证以下事实可稳定查询：

- 一个文件属于哪个模块；
- 一个文件大概率承担什么职责；
- 一个文件是否有状态、线程、互操作风险；
- 一个文件是否值得优先进入首批 Translation Unit 候选。

---

## 3.4 符号层

### 3.4.1 `symbol`

建议把符号层视为最重要的“翻译可寻址对象层”。

建议字段分组如下：

- **标识信息**：符号 ID、名称、全名、所属文件、源码范围；
- **分类信息**：符号种类、可见性、命名空间、所属模块；
- **职责信息**：角色标签、是否公共接口、是否适合作为 TU 根节点；
- **风险信息**：状态敏感、线程敏感、互操作敏感、生命周期敏感；
- **验证信息**：是否绑定验证锚点、是否有历史失败记录。

### 3.4.2 符号种类建议

建议至少区分：

- `class`
- `interface`
- `object / singleton`
- `enum`
- `type alias`
- `function`
- `method`
- `property`
- `store / signal`
- `lifecycle handler`
- `router registration`

### 3.4.3 `symbol_signature`

建议把 `symbol_signature` 设计成“面向压缩和对齐的语义壳层”，而不是完整语法树镜像。

建议字段分组如下：

- **签名信息**：参数、返回值、泛型、可见性；
- **副作用信息**：是否读状态、写状态、发请求、发事件、触发 UI 更新；
- **边界信息**：是否跨线程、是否接触 Native 边界、是否依赖生命周期；
- **错误信息**：错误输出方式、失败症状、默认值语义；
- **压缩信息**：适合进入 Repo Map 的摘要版本。

### 3.4.4 符号层设计原则

- 能靠签名表达的语义，不必在 Repo Map 中重复全文；
- 能作为独立 TU 根节点的符号，应被显式标记；
- 低置信度符号识别结果不能直接进入高优先级翻译流程。

---

## 3.5 关系层

## 3.5.1 `import_edge` / `export_edge`

用于表达模块级依赖方向。

建议重点记录：

- 源文件与目标文件；
- 引入名与导出名；
- 类型级依赖或运行时依赖；
- 是否构成循环依赖；
- 解析置信度；
- 是否属于后续闭包计算中的强依赖候选。

## 3.5.2 `call_edge`

用于表达行为依赖方向。

建议重点记录：

- 调用方与被调方；
- 调用位置；
- 同步 / 异步 / 回调 / 事件驱动类型；
- 是否跨模块、跨线程、跨边界；
- 是否需要在 Repo Map 中高亮显示。

## 3.5.3 `inheritance_edge`

用于表达接口、抽象类和协议边界。

建议重点记录：

- 实现关系类型；
- 是否属于必须先翻译的上游；
- 是否为 contract 级强依赖；
- 是否对 Verify 的实现无关测试有直接影响。

---

## 3.6 风险与边界标记层

### 3.6.1 `state_edge`

`state_edge` 不只是“变量引用”，而是“谁拥有状态、谁能写、谁能读、谁持久化”。

建议字段分组如下：

- 状态拥有者；
- 读取方；
- 写入方；
- 持久化方；
- 生命周期范围；
- 一致性等级；
- 是否跨页面共享；
- 是否跨线程写入；
- 是否直接驱动 UI。

### 3.6.2 `thread_boundary_marker`

建议至少标记以下几类线程边界：

- 主线程 UI 提交点；
- 后台计算点；
- 异步回调入口；
- 长任务调度点；
- Native 回调切回点。

### 3.6.3 `interop_boundary_marker`

建议至少标记以下信息：

- ArkTS / 仓颉 / C / Native / TDLib 边界类型；
- 数据交换方向；
- 生命周期与内存管理要求；
- 错误传播方式；
- 是否必须独立成 TU；
- 对应 Verify 建议。

### 3.6.4 `ui_binding_marker`

建议至少标记：

- 页面与状态绑定关系；
- 页面与事件绑定关系；
- 路由参数注入点；
- 长列表、虚拟化、批量更新区域；
- 生命周期敏感 UI 更新点。

---

## 3.7 验证与诊断层

### 3.7.1 `verification_anchor`

建议把 `verification_anchor` 视为连接“索引事实”和“验证流程”的桥梁。

建议字段包括：

- 关联文件 / 符号 / 模块；
- 推荐验证类型；
- 可观察行为；
- 页面路径或功能入口；
- 成功判定；
- 典型失败症状；
- 是否允许实现无关评判。

### 3.7.2 `diagnostic_hint`

建议用于沉淀：

- 常见错误模式；
- 可能根因；
- 推荐补拉上下文；
- 推荐修复方向；
- 已知关联 Pattern。

---

## 4. Repo Index 构建流程设计

## 4.1 构建阶段拆分

建议把索引构建拆成四步：

1. **文件发现与快照建立**：记录仓库版本、文件集合和构建范围；
2. **语法抽取**：通过解析器抽 AST、符号、基础边关系；
3. **规则增强**：识别架构角色、状态边界、线程边界、互操作边界；
4. **验证增强**：补充验证锚点、诊断提示和置信度。

## 4.2 规则增强策略

建议使用三种规则源：

- **语法规则**：基于 AST 节点和结构模板；
- **命名规则**：基于目录、文件名、符号命名和约定；
- **工程规则**：基于路由入口、页面目录、配置文件和样本结构。

### 4.2.1 规则增强的边界

当前阶段不追求 100% 自动识别，而追求：

- 高价值区域识别稳定；
- 低置信度区域显式标记；
- 不把猜测伪装成事实。

## 4.3 增量更新策略

建议增量更新按以下顺序传播：

1. 直接改动文件重建；
2. 其导入导出邻居进入影响集合；
3. 其状态拥有者和调用邻居进入影响集合；
4. 受影响模块的 Repo Map 重算；
5. 受影响 TU 的闭包缓存失效。

---

## 5. Repo Map 详细设计

## 5.1 三视图策略

建议始终同时产出以下三视图：

### 5.1.1 `repo_index.sqlite`

作用：

- 脚本查询主存；
- 支持闭包计算、风险查询、增量更新；
- 便于人工 SQL spot check。

### 5.1.2 `repo_map.jsonl`

作用：

- 作为模块级或 TU 级的结构化检索中间层；
- 便于按节点拼装上下文；
- 便于记录预算、强弱依赖、风险标签。

### 5.1.3 `repo_map.txt`

作用：

- 作为模型投喂时的压缩卡片集；
- 让 LLM 快速理解模块角色、边界和验证入口；
- 不承担精确查询责任。

---

## 5.2 JSONL 节点模型

建议 `repo_map.jsonl` 每行对应一个“可独立摘要、可独立组装”的节点。

节点类型建议包括：

- `module`
- `file`
- `tu-candidate`
- `risk-cluster`
- `verification-cluster`

### 5.2.1 节点字段建议

每个 JSONL 节点建议至少包含：

- 节点 ID；
- 节点类型；
- 文件路径或模块路径；
- 架构角色；
- 关键职责；
- 关键符号；
- 强依赖列表；
- 弱依赖列表；
- 风险标签；
- 推荐 Skill；
- 推荐验证方式；
- token 预算估算；
- 是否常驻上下文。

### 5.2.2 节点粒度选择原则

- 过粗：脚本难以做精确拼装；
- 过细：LLM 上下文被碎片淹没；
- 当前阶段建议以“模块卡片 + TU 候选卡片”为主，不建议把每个局部函数都直接投影成独立卡片。

---

## 5.3 TXT 结构化压缩格式

建议 `repo_map.txt` 采用“模块卡片簇”的组织方式。

每张卡片建议按以下顺序输出：

1. 模块名与路径；
2. 模块角色；
3. 关键职责；
4. 公开接口；
5. 强依赖；
6. 下游影响；
7. 状态所有权摘要；
8. 线程与 UI 边界摘要；
9. 互操作边界摘要；
10. 推荐翻译顺序；
11. 推荐验证方法。

### 5.3.1 压缩优先级

保留优先级建议如下：

1. 边界与契约
2. 公开接口与依赖方向
3. 状态与线程风险
4. 验证锚点
5. 实现细节摘要

如果 token 不足，应先牺牲低价值实现细节，而不是牺牲契约与风险摘要。

---

## 5.4 强依赖 / 弱依赖投影规则

### 5.4.1 强依赖进入原则

建议以下信息默认进入首轮闭包：

- 直接实现或继承的接口与抽象；
- 当前 TU 直接读写的状态拥有者；
- 当前 TU 直接调用的关键服务和桥接接口；
- 当前 TU 所依赖的线程切换规则；
- 当前 TU 验证 oracle 所依赖的功能锚点。

### 5.4.2 弱依赖保留原则

建议以下信息仅作为候选补拉项保留：

- 长尾 UI 细节组件；
- 异常路径中的工具模块；
- 仅影响非关键交互的样式或辅助逻辑；
- 与当前 TU 不共享状态和 contract 的邻近模块。

---

## 5.5 查询契约设计

虽然当前阶段不写实现代码，但建议后续实现时优先支持以下查询能力：

1. 给定文件 / 符号，查询其强依赖闭包；
2. 给定错误类型，查询最相关的补拉上下文；
3. 给定模块，查询其风险聚类卡片；
4. 给定 TU 候选，查询其建议 Skill、Pattern 与验证锚点；
5. 给定快照差异，查询受影响 TU 列表。

这些查询能力将直接决定后续编排层是否真正做到“错误驱动而非全文重喂”。

---

## 5.6 数据质量与人工核查口径

当前阶段建议至少记录以下质量指标：

- 文件解析成功率；
- 关键符号识别率；
- 关键模块角色识别覆盖率；
- 状态边界识别覆盖率；
- 主线程 / 异步边界识别覆盖率；
- 高风险模块误判率；
- 强依赖闭包命中率；
- 因索引不足导致的 Repair 比例。

### 5.6.1 人工 Spot Check 建议

每轮索引构建后，建议至少人工检查：

- 一个页面模块；
- 一个状态模块；
- 一个服务模块；
- 一个互操作或桥接模块；
- 一个复杂长列表或虚拟化相关模块。

Spot check 的重点不是“抽取是否完美”，而是：

- 高风险事实有没有被漏掉；
- 强依赖有没有被误判为弱依赖；
- Repo Map 是否足够解释模块职责与边界。

---

## 6. 与后续编排层的接口边界

为了让数据层不与编排层耦合过深，建议明确以下边界：

- 数据层负责提供事实、标签、摘要、查询接口；
- 编排层负责决定何时查询、查多少、如何拼成 Prompt 或审查输入；
- 数据层不负责决定模型角色；
- 数据层不直接做修复判断，但要为修复提供可追索事实。

---

## 7. 当前阶段落地建议

建议按以下顺序推进后续实现：

1. 先打通 `repository_snapshot + source_file + symbol + import_edge` 最小链路；
2. 再补 `state_edge + thread_boundary_marker + interop_boundary_marker` 三个高价值标记层；
3. 之后再做 `repo_map.jsonl` 与 `repo_map.txt` 双视图；
4. 最后才做更精细的查询排序和预算裁剪。

---

## 8. 总结

本设计的核心思想是：`Repo Index` 提供事实底座，`Repo Map` 提供任务压缩视图。二者一起决定后续翻译流程能否做到：

- 首轮上下文最小化；
- 错误驱动补拉精确化；
- 风险边界显式化；
- 失败回溯可解释化。

如果数据层没有先把“状态、线程、互操作、验证锚点”这些高价值事实固定下来，那么后续任何看起来聪明的多 Agent 编排都只是建立在脆弱上下文之上的表面优化。
