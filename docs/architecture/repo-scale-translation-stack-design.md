# 仓库级代码翻译栈设计蓝图（Repo-Scale Translation Stack Design）

## 1. 文档目的

本文用于定义本项目从“小样本 Skill / 样本验证”升级到“仓库级 ArkTS → 仓颉翻译”时的核心中间层设计。

本文重点回答以下问题：

1. 如何为大型 ArkTS 仓库建立可计算、可压缩、可检索的 `Repo Index`；
2. 如何从 `Repo Index` 派生出同时服务脚本与大模型的 `Repo Map`；
3. 如何把一个大型页面或模块切分为可验证的 `Translation Unit`；
4. `Translate → Review → Verify → Repair` 四段流水线之间应交换什么工件，如何触发错误驱动检索；
5. 如何把成功经验与失败经验沉淀为可复用的 `Pattern Memory`，让流水线越跑越稳。

本文是架构设计文档，不包含 Python / 仓颉实现代码，也不直接约束某个脚本的最终 CLI 形态。本文的目标是给后续实现提供统一蓝图，避免中间层设计漂移。

---

## 2. 设计范围与非目标

### 2.1 本文覆盖范围

本文覆盖以下五层设计：

- `L1 Repo Index`：仓库级结构索引层；
- `L2 Repo Map`：面向脚本与模型的结构压缩层；
- `L3 Translation Unit`：可验证翻译单元切分层；
- `L4 Orchestration`：翻译、审查、验证、修复编排层；
- `L5 Pattern Memory`：经验沉淀与失败回写层。

### 2.2 本文明确不覆盖的内容

当前阶段，本文明确不展开以下内容：

- 不定义最终 Python 包结构；
- 不定义具体数据库建表 SQL；
- 不直接绑定某个模型供应商或 API 网关；
- 不直接设计 Telegram 全仓一键翻译策略；
- 不把图数据库、向量库、MCP 服务端作为当前阶段的硬依赖。

### 2.3 设计原则

本文整体遵守以下原则：

1. **结构优先于 Prompt。** 大模型看到的上下文应来自结构化中间层，而不是人工拼接全文。
2. **依赖闭包优先于全仓喂入。** 任何翻译请求都应先缩到最小必要上下文。
3. **可验证优先于可生成。** 不能被编译、测试或行为证据约束的翻译单元，不应进入批量流程。
4. **边界优先于语法。** 状态、线程、生命周期、互操作边界决定大型工程翻译成败。
5. **失败资产必须回写。** 每一轮失败都要产出新的分类、规则或检索线索，而不是只留下日志。

---

## 3. 总体架构概览

建议将仓库级翻译栈组织为以下数据流：

```text
源仓库（ArkTS / HarmonyOS 工程）
    ↓
L1：Repo Index 构建
    ↓
L2：Repo Map 生成（SQLite / JSONL / TXT）
    ↓
L3：Translation Unit 切分与依赖闭包打包
    ↓
L4：Translate → Review → Verify → Repair
    ↓
L5：Pattern Memory / Trace / Failure Taxonomy 回写
```

各层职责必须严格分离：

- `Repo Index` 负责“把仓库变成结构化数据”；
- `Repo Map` 负责“把结构化数据压缩成可检索、可投喂、可摘要的地图”；
- `Translation Unit` 负责“把翻译目标切成可控、可验证、可复用的作战单元”；
- `Orchestration` 负责“围绕证据驱动生成、审查、验证和修复”；
- `Pattern Memory` 负责“把一次性运行结果沉淀成长期资产”。

如果上述职责混杂，例如把 Repo Map 逻辑写进 Prompt 构造器，把失败修复逻辑写进单次大模型调用，就会导致后续很难定位性能瓶颈、质量瓶颈和上下文漂移问题。

---

## 4. 第一部分：数据与地图层（L1 & L2）

## 4.1 Repo Index 的定位

`Repo Index` 不是“代码搜索结果缓存”，而是本项目所有仓库级智能行为的事实底座。

它必须服务于以下四类问题：

1. **依赖闭包计算**：当前翻译单元最少需要哪些文件、符号、契约；
2. **检索过滤与排序**：哪些上下文必须优先进入模型，哪些只需在错误时补拉；
3. **Translation Unit 切分**：哪些代码应该拆开翻，哪些必须作为整体处理；
4. **失败回溯**：一次编译错误、线程错误或状态错误应追溯到哪类边界、哪批依赖。

因此，`Repo Index` 不能只记录 `import` 和 `class name`，还必须显式记录架构角色、边界风险和验证锚点。

---

## 4.2 Repo Index 数据模型

建议把 `Repo Index` 设计为“关系型主存 + 查询层图视图”的结构：

- 主存使用 `SQLite`；
- 查询时按需在内存中构造依赖图、调用图和风险图；
- 当前阶段不把图数据库作为硬依赖。

这样做的原因是：

- `SQLite` 足够支撑本项目早期的增量索引与复杂查询；
- 调试成本低，便于用脚本、人工和 LLM 三种方式共同核查；
- 后续如果确有必要，再把热点查询投影到图数据库，不会推翻前期资产。

### 4.2.1 核心实体

建议至少建立以下实体层：

1. `repository_snapshot`
2. `source_file`
3. `symbol`
4. `symbol_signature`
5. `import_edge`
6. `export_edge`
7. `call_edge`
8. `inheritance_edge`
9. `state_edge`
10. `thread_boundary_marker`
11. `interop_boundary_marker`
12. `ui_binding_marker`
13. `verification_anchor`
14. `diagnostic_hint`

### 4.2.2 建议字段范围

#### A. `repository_snapshot`

用于记录一次索引对应的源仓库快照。

建议包含：

- 仓库来源 URL；
- 拉取日期；
- 分支；
- commit hash；
- 仓库类型标识；
- 解析器版本；
- 索引生成时间；
- 是否完整索引或增量索引。

作用是保证所有后续翻译和失败回溯都能定位到具体源版本，避免“上下文来自不同版本”的污染。

#### B. `source_file`

用于记录文件级事实。

建议包含：

- 文件路径；
- 模块路径；
- 语言类型；
- 文件大小；
- 哈希；
- 解析状态；
- 文件职责标签；
- 所属架构层；
- 是否入口文件；
- 是否测试文件；
- 是否生成文件；
- 是否高风险边界文件。

其中，“文件职责标签”建议至少支持：

- `page`
- `component`
- `viewmodel`
- `state`
- `service`
- `model`
- `repository`
- `router`
- `signal`
- `interop`
- `native-bridge`
- `config`
- `test`

#### C. `symbol`

用于记录可被翻译、可被引用、可被检索的符号。

建议包含：

- 符号唯一 ID；
- 符号名；
- 符号种类；
- 所属文件；
- 起止位置；
- 可见性；
- 所属命名空间；
- 所属角色标签；
- 所属线程风险标签；
- 所属状态风险标签；
- 是否建议独立翻译。

符号种类建议至少覆盖：

- `class`
- `interface`
- `struct-like object`
- `enum`
- `type alias`
- `function`
- `method`
- `property`
- `signal/store`
- `hook / lifecycle handler`
- `router registration`

#### D. `symbol_signature`

用于记录符号的可压缩语义壳层。

建议包含：

- 参数列表概要；
- 返回值概要；
- 泛型信息；
- 抛错 / 失败语义；
- 输入输出副作用摘要；
- 生命周期说明；
- 状态读写摘要；
- 线程约束摘要；
- 互操作约束摘要。

此层不是完整代码正文，而是后续 `Repo Map` 压缩时最重要的素材。

#### E. `import_edge` / `export_edge`

用于记录模块级依赖方向。

建议包含：

- 源文件；
- 目标文件；
- import / export 类型；
- 引用名列表；
- 是否类型级依赖；
- 是否运行时依赖；
- 是否循环依赖；
- 解析置信度。

#### F. `call_edge`

用于记录函数 / 方法之间的调用关系。

建议包含：

- caller 符号；
- callee 符号；
- 调用种类；
- 是否异步边界；
- 是否跨线程调度；
- 是否涉及 UI 提交；
- 是否跨模块；
- 是否经过 service locator / dependency injection；
- 解析置信度。

#### G. `inheritance_edge`

用于记录类型与抽象层关系。

建议包含：

- 子类型符号；
- 父类型符号；
- 实现 / 继承 / 混入关系；
- 是否关键协议边界；
- 是否必须先翻译父类型。

#### H. `state_edge`

用于记录状态读写关系，而不是只记录变量定义。

建议包含：

- 状态拥有者符号；
- 读取方符号；
- 写入方符号；
- 持久化方；
- 状态类型；
- 生命周期范围；
- 一致性风险等级；
- 是否直接驱动 UI；
- 是否跨页面共享；
- 是否跨线程写入。

这一层对 Telegram 级别项目尤其关键，因为真实翻译失败常常不是语法错误，而是“状态所有权被翻坏”。

#### I. `thread_boundary_marker`

用于标记线程 / 执行拓扑风险点。

建议包含：

- 所属符号；
- 边界类型；
- 来源线程；
- 目标线程；
- 是否必须切回主线程；
- 是否为后台计算点；
- 是否为回调入口；
- 风险说明；
- 对应验证建议。

#### J. `interop_boundary_marker`

用于记录 ArkTS / Native / C-Interop / TDLib 等边界。

建议包含：

- 所属文件 / 符号；
- 边界种类；
- 数据交换方向；
- 所需桥接层；
- 所需内存 / 生命周期说明；
- 错误传播语义；
- 是否需要主线程提交；
- 是否建议独立翻译与验证。

#### K. `ui_binding_marker`

用于记录页面、组件、状态绑定与路由绑定关系。

建议包含：

- 页面 / 组件符号；
- 绑定状态源；
- 绑定事件源；
- 路由入口 / 出口；
- 生命周期钩子；
- 是否涉及长列表、批量更新、虚拟化渲染；
- 是否对性能敏感。

#### L. `verification_anchor`

用于给后续验证流程提供可执行锚点。

建议包含：

- 关联文件 / 符号；
- 建议验证类型；
- 对应页面 / 功能路径；
- 对应单元测试或 mock contract 名称；
- 必须观察的行为信号；
- 成功判定；
- 典型失败症状。

#### M. `diagnostic_hint`

用于沉淀与错误分类、修复检索相关的附加线索。

建议包含：

- 错误模式；
- 常见根因；
- 推荐补拉上下文；
- 推荐修复方向；
- 已关联 Skill；
- 已关联 Pattern Memory 条目。

---

## 4.3 Repo Index 的关系视图

尽管主存是关系型，查询层仍应显式支持以下视图：

1. **模块依赖图**：文件 / 模块之间的导入导出关系；
2. **符号调用图**：函数、方法、Service、ViewModel、State 之间的调用关系；
3. **状态所有权图**：谁拥有状态、谁读、谁写、谁持久化；
4. **执行拓扑图**：后台处理、主线程提交、回调入口和异步链；
5. **边界风险图**：UI、状态、互操作、生命周期等高风险点的分布。

对于当前项目而言，最有价值的不是构建“全知全能大图”，而是让这五种视图都能被脚本快速投影出来，服务具体翻译任务。

---

## 4.4 Repo Index 的构建策略

建议采用“静态解析为主，规则补丁为辅，正则兜底”的构建策略。

### 4.4.1 解析层级

可将解析分为三层：

1. **语法层**：由 Tree-sitter 等解析器抽取 AST 与基础节点关系；
2. **语义层**：基于规则识别架构角色、状态所有权、生命周期钩子、异步边界；
3. **工程层**：识别构建入口、页面入口、资源路径、配置与验证锚点。

### 4.4.2 置信度原则

所有自动抽取结果都建议带置信度，至少分为：

- `high`：解析器直接确认；
- `medium`：由规则组合推出；
- `low`：正则或启发式猜测。

这样做的目的是：

- 低置信度边不应直接成为强依赖；
- 审查阶段可以优先核查低置信度高风险区域；
- 失败修复时能更准确判断是“翻译错误”还是“索引误判”。

### 4.4.3 增量更新策略

建议从一开始就支持“按快照增量更新”，而不是每次全量重建。

增量策略应至少满足：

- 文件哈希变化时重建该文件的局部索引；
- 上下游强依赖文件进入受影响列表；
- Repo Map 仅重算受影响模块与受影响 Translation Unit；
- 失败修复时可临时构造局部增量视图。

---

## 4.5 Repo Map 的定位

`Repo Map` 是 `Repo Index` 的任务化压缩投影，而不是普通摘要。

它必须同时服务两类对象：

1. **脚本 / Orchestrator**：需要结构化、稳定、可过滤、可拼装；
2. **LLM**：需要低 token、高信息密度、能够快速理解架构角色与边界。

因此，建议把 `Repo Map` 设计为三份并行产物：

- `repo_index.sqlite`：主查询存储；
- `repo_map.jsonl`：脚本遍历与筛选视图；
- `repo_map.txt`：模型投喂压缩视图。

当前阶段不建议只做一个 `txt` 文件，否则很快会遇到以下问题：

- 查询逻辑与文本格式耦合；
- 难以做增量更新；
- 难以区分“强依赖上下文”和“补充参考上下文”；
- 难以在失败回路中按类别追加上下文。

---

## 4.6 Repo Map 生成规则

### 4.6.1 生成目标

Repo Map 的压缩不是简单删字，而是保留最有助于翻译与验证的结构信息。

应保留：

- 模块角色；
- 关键符号；
- 公共接口 / 调用方向；
- 状态所有权；
- 线程 / 主线程边界；
- 互操作边界；
- 关键路由与页面入口；
- 推荐验证锚点；
- 高风险提示。

应主动牺牲：

- 大段实现正文；
- 低价值局部变量细节；
- 可由签名推断的重复样板；
- 与当前 Translation Unit 无关的邻近模块细节。

### 4.6.2 压缩顺序

建议按以下顺序压缩：

1. **文件 → 架构角色归类**
2. **文件内符号 → 公共符号与关键私有符号筛选**
3. **边关系 → 强依赖、弱依赖、风险边三分**
4. **状态与线程 → 约束优先保留**
5. **验证锚点 → 与当前任务最相关的功能路径保留**

这样做的原因是：

- 大模型更容易先理解“这个模块是干什么的”；
- 约束类信息比实现细节更难通过后验修补；
- 一旦丢掉状态与线程信息，后续 Repair 的成本会显著上升。

### 4.6.3 JSONL 视图设计

建议 `repo_map.jsonl` 中每一行代表一个“可独立检索与拼装的模块节点”。

每条记录建议至少包含：

- 节点 ID；
- 节点类型；
- 文件路径；
- 架构角色；
- 模块摘要；
- 关键符号列表；
- 强依赖节点列表；
- 弱依赖节点列表；
- 风险边界标签；
- 推荐搭配 Skill；
- 推荐验证锚点；
- token 预算估计；
- 是否适合作为基础上下文常驻。

这种设计便于脚本做：

- TU 闭包打包；
- 错误驱动补拉；
- 预算裁剪；
- 多模块并行准备；
- 人工 spot check。

### 4.6.4 TXT 视图设计

建议 `repo_map.txt` 采用“模块卡片 + 风险摘要 + 依赖列表”的结构化文本，而不是普通目录树。

每个模块卡片建议包含：

- 模块名 / 路径；
- 模块角色；
- 关键职责；
- 公开接口符号；
- 依赖上游；
- 依赖下游；
- 状态所有权摘要；
- 线程 / UI 边界摘要；
- 互操作边界摘要；
- 翻译优先级；
- 建议验证方式。

### 4.6.5 强依赖与弱依赖规则

Repo Map 生成时，建议把依赖分成两级：

#### 强依赖

满足以下任一条件的依赖，默认进入 Translation Unit 的基础上下文：

- 当前单元直接调用；
- 当前单元实现其接口或继承其抽象；
- 当前单元读写其状态；
- 当前单元依赖其线程 / 生命周期约束；
- 当前单元依赖其互操作契约；
- 当前单元必须通过其验证锚点判断正确性。

#### 弱依赖

满足以下条件的依赖，默认不进入首轮上下文，但要保留可追索入口：

- 只在异常路径或长尾分支中出现；
- 只提供附属工具或低频 UI 细节；
- 只在错误分类指向时才需要解释；
- 当前首轮翻译不影响其行为等价性。

### 4.6.6 风险优先压缩策略

建议所有压缩过程都优先保留以下风险信息：

- `main-thread boundary`
- `state ownership`
- `cache consistency`
- `interop / native bridge`
- `long-list / batch update / virtualization`
- `routing + parameter passing`
- `lifecycle-sensitive side effects`

这些风险信息决定了后续修复成本，不应被当作“细枝末节”压掉。

---

## 5. 第二部分：翻译单元与编排层（L3 & L4 & L5）

## 5.1 Translation Unit 的定位

`Translation Unit` 不是“某个文件的一次翻译任务”，而是“一个职责边界清晰、依赖闭包可计算、验证口径明确的最小作战单元”。

Translation Unit 的设计直接决定：

- 模型上下文是否足够；
- 审查是否能针对性开展；
- 验证是否可执行；
- 失败是否能局部修复而不引发全仓回滚。

如果把一个 5000 行 ArkTS 页面直接当成一个 TU，结果通常会出现三类问题：

1. 上下文超载，模型只能做局部表面翻译；
2. 线程、状态、生命周期边界被混在一起，审查无法精确指出问题；
3. 任何一个子区域失败都会拖着整页反复重生，迭代成本极高。

因此，TU 必须以“职责”和“验证可行性”为核心切分，而不是以文件为核心切分。

---

## 5.2 Translation Unit 的类型体系

建议至少定义以下 TU 类型：

1. `UI Shell Unit`
2. `State Core Unit`
3. `ViewModel / Presenter Unit`
4. `Service Adapter Unit`
5. `Domain Model Unit`
6. `Router / Navigation Unit`
7. `Interop Bridge Unit`
8. `Persistence Unit`
9. `Reactive Pipeline Unit`
10. `Verification Harness Unit`

### 5.2.1 各类型的典型职责

#### A. `UI Shell Unit`

聚焦页面结构、组件组合、事件分发入口，不直接承载复杂业务状态写入逻辑。

#### B. `State Core Unit`

聚焦状态定义、所有权、衍生字段、可变字段、生命周期与一致性规则。

#### C. `ViewModel / Presenter Unit`

聚焦事件处理、状态过渡、异步效果发起和 UI 提交组织。

#### D. `Service Adapter Unit`

聚焦业务服务接口、请求上下文管理、错误模型映射与下游依赖包装。

#### E. `Domain Model Unit`

聚焦类型定义、协议对象、输入输出约束、序列化映射和不可变语义。

#### F. `Router / Navigation Unit`

聚焦路由注册、参数传递、页面切换与生命周期承接。

#### G. `Interop Bridge Unit`

聚焦 Native / C / TDLib 等边界上的 ABI、内存、线程和错误传播。

#### H. `Persistence Unit`

聚焦本地存储接口、缓存回填、持久化时机和一致性约束。

#### I. `Reactive Pipeline Unit`

聚焦 Signal、事件流、批量合并、节流、防抖与 UI 刷新拓扑。

#### J. `Verification Harness Unit`

聚焦 mock、测试支架、行为对拍输入输出，不直接作为业务迁移单元，但为验证提供锚点。

---

## 5.3 复杂页面的切分规范

面对一个 5000 行的 ArkTS 复杂页面，建议遵循“先剥边界，再剥职责，最后剥视图”的切分顺序。

### 5.3.1 第一步：识别高风险边界

先识别页面内以下区域：

- 路由入口与参数注入；
- 状态定义与状态拥有者；
- 异步效果发起点；
- Signal / Store / Cache 接入点；
- Native / TDLib / C-Interop 回调入口；
- 主线程 UI 提交点；
- 长列表与批量更新逻辑；
- 生命周期钩子与资源释放点。

这些区域不应作为 UI 代码正文的一部分被整体吞掉，而应优先剥离成独立 TU 或独立契约。

### 5.3.2 第二步：识别职责分层

对于大页面，建议至少拆出以下层：

1. `Page Route Adapter`
2. `Page State Core`
3. `Page Event Reducer / Dispatcher`
4. `Async Effect Coordinator`
5. `UI Composition Shell`
6. `List / Cell Rendering Subunit`
7. `External Service / Store Adapter`

若页面还承担 Native 回调或复杂虚拟列表逻辑，应再拆出：

8. `Interop Callback Bridge`
9. `Timeline Delta Merge Unit`
10. `Virtualization Policy Unit`

### 5.3.3 第三步：按可验证性再收缩

如果某一层仍然过大，则继续按“是否能独立验证”收缩：

- 能被单元测试和 mock contract 验证的逻辑优先独立；
- 能被页面快照或交互路径验证的 UI 逻辑保持在 UI Shell；
- 不能脱离互操作边界验证的逻辑拆为 Interop Bridge；
- 需要线程 / 生命周期约束的逻辑拆为独立 TU，并在 TU 元数据中显式声明约束。

---

## 5.4 Translation Unit 的元数据规范

建议每个 TU 都至少携带以下元数据：

- TU ID；
- TU 类型；
- 来源文件与符号范围；
- 目标输出路径；
- 责任边界说明；
- 强依赖列表；
- 弱依赖列表；
- 相关 Skill 列表；
- 相关 Pattern Memory 列表；
- 线程约束；
- 状态所有权说明；
- 互操作约束；
- 验证 oracle；
- 预算信息；
- 风险等级；
- 建议翻译顺序。

这样做的原因是：

- Translate 阶段不需要自己重新猜“这段代码是什么角色”；
- Review 阶段可直接对照约束检查；
- Verify 阶段能直接选择合适的验证器；
- Repair 阶段可按 TU 粒度局部回滚和重试。

---

## 5.5 依赖闭包（Dependency Closure）计算规则

依赖闭包不应理解为“把所有能连到的文件都塞给模型”，而应理解为“给定 TU 后，为保证其首轮翻译与验证成立所需的最小必要上下文”。

建议采用“两层闭包”策略：

### 5.5.1 基础闭包（Base Closure）

首轮翻译默认带入，通常包括：

- 当前 TU 自身的源片段；
- 直接导入的公共接口；
- 直接调用的关键符号签名；
- 当前 TU 所读写的状态拥有者定义；
- 当前 TU 所依赖的线程 / 生命周期契约；
- 当前 TU 相关的 Skill 与 Pattern Memory；
- 当前 TU 的验证锚点摘要。

### 5.5.2 扩展闭包（Extended Closure）

只在错误驱动检索中按需追加，通常包括：

- 异常路径依赖；
- 长尾 UI 细节；
- 间接调用链上的二跳依赖；
- 历史失败中经常遗漏的辅助模块；
- 特定错误分类指向的边界上下文。

### 5.5.3 强依赖判定规则

建议以下关系视为强依赖：

- 直接实现 / 继承关系；
- 直接状态读写关系；
- 直接异步调度关系；
- 主线程切换点；
- 互操作桥接边界；
- 当前 oracle 依赖的功能锚点。

### 5.5.4 弱依赖判定规则

建议以下关系视为弱依赖：

- 仅在错误分支或附属分支中使用；
- 不影响当前 TU 类型正确性的工具类；
- 只提供视觉细节、不影响 contract 的组件；
- 可由后续 TU 独立处理的邻近逻辑。

### 5.5.5 闭包预算原则

闭包必须携带预算信息，例如：

- 代码正文预算；
- 签名摘要预算；
- Repo Map 摘要预算；
- Skill 数量预算；
- Pattern Memory 数量预算。

一旦超预算，优先删除低置信度弱依赖，而不是删除状态、线程和边界契约。

---

## 5.6 Orchestration：Translate → Review → Verify → Repair

建议把流水线视为“工件传递系统”，而不是“四次大模型聊天”。

每一阶段都应有明确输入、输出和失败条件。

### 5.6.1 Translate 阶段

#### 输入

- Translation Unit 元数据；
- Base Closure；
- Repo Map 摘要；
- 相关 Skill；
- 相关 Pattern Memory；
- 目标语言约束；
- 输出目标与验证要求。

#### 输出

- 候选目标代码；
- 目标文件清单；
- 关键映射说明；
- 自述的风险点；
- 自述的不确定点；
- 建议优先验证项。

#### 失败条件

- 明显违反 TU 类型边界；
- 明显遗漏强依赖接口；
- 明显混淆线程或状态所有权；
- 输出不可落盘或不可编译。

### 5.6.2 Review 阶段

Review 的职责不是“挑语法毛病”，而是做架构契约审查。

#### 输入

- 候选代码；
- TU 元数据；
- 相关 Skill；
- 相关 Pattern Memory；
- Repo Map 中与该 TU 相邻的风险摘要。

#### 输出

- 结构化问题清单；
- 问题等级；
- 问题类型；
- 对应证据；
- 推荐修复方向；
- 是否允许进入 Verify。

#### 重点检查项

- 是否破坏状态所有权；
- 是否误把后台结果直接推进 UI 主线程；
- 是否破坏 Signal / Store / Cache 的语义；
- 是否遗漏互操作边界契约；
- 是否引入生命周期泄漏；
- 是否与 TU 预定职责边界不符。

### 5.6.3 Verify 阶段

Verify 必须优先依赖“可执行证据”，而不是再做一轮语言审查。

#### 输入

- 审查通过的候选代码；
- 落盘后的目标工程快照；
- TU 验证 oracle；
- 对应 mock / 单测 / 页面路径信息。

#### 输出

- 编译结果；
- 测试结果；
- 页面 / 行为验证结果；
- 失败分类；
- 诊断日志；
- 是否进入 Repair。

#### 建议验证类型

- `compile verification`
- `unit test verification`
- `mock contract verification`
- `behavioral trace comparison`
- `UI smoke verification`

### 5.6.4 Repair 阶段

Repair 不是重开新局，而是基于失败证据做最小上下文补强与局部修复。

#### 输入

- 失败分类；
- 编译 / 测试 / 行为证据；
- 已翻译代码；
- 原 TU 元数据；
- 错误驱动补拉上下文。

#### 输出

- 修复后的候选代码；
- 修复说明；
- 新增上下文说明；
- 若仍失败，则输出结构化根因分析。

Repair 的目标不是让模型“再努力一次”，而是把失败证据转化为“精确补上下文 + 精确改一类问题”。

---

## 5.7 错误驱动检索机制

错误驱动检索是整个流水线的关键增益点。

其核心思想是：

- 首轮翻译只带最小必要闭包；
- 一旦验证失败，不做全文重喂；
- 先对失败分类，再按类别定向补拉上下文；
- 每种错误类型都有不同的上下文补拉策略。

### 5.7.1 建议错误分类

建议至少区分以下错误大类：

1. `missing symbol`
2. `signature mismatch`
3. `state contract violation`
4. `thread / main-thread violation`
5. `interop boundary violation`
6. `lifecycle leak or invalid ownership`
7. `behavior mismatch`
8. `verification harness mismatch`
9. `retrieval insufficiency`
10. `index quality issue`

### 5.7.2 各类错误的补拉方向

#### A. `missing symbol`

优先补拉：

- 目标符号定义；
- 符号签名；
- 直接调用上游；
- 导入导出链路。

#### B. `signature mismatch`

优先补拉：

- 父接口定义；
- 相关实现类签名；
- 参数和返回值约束；
- 历史 Pattern Memory 中相似映射。

#### C. `state contract violation`

优先补拉：

- 状态拥有者定义；
- 状态读写边；
- 持久化策略；
- 衍生字段与只读字段说明。

#### D. `thread / main-thread violation`

优先补拉：

- 执行拓扑标记；
- UI 提交点；
- 异步边界；
- 生命周期钩子。

#### E. `interop boundary violation`

优先补拉：

- Bridge 契约；
- 错误传播规则；
- 数据结构映射；
- 线程切换说明；
- Native 生命周期说明。

#### F. `behavior mismatch`

优先补拉：

- 原实现行为轨迹；
- mock contract；
- 对拍输入输出；
- 邻近 TU 的联动上下文。

### 5.7.3 检索触发时机

建议在以下节点触发错误驱动检索：

- Translate 产物被 Review 拦截，且问题指向缺失上下文；
- Verify 阶段出现可归因的编译或测试错误；
- Repair 连续两轮仍失败，怀疑是闭包不完整；
- 某类错误在同一模块内重复出现，说明 Repo Map 压缩过度。

---

## 5.8 Verification Oracle 设计原则

每个 TU 都必须提前定义验证 oracle，而不是翻译完再想怎么测。

建议 oracle 至少包括以下要素：

- 验证类型；
- 可执行入口；
- 观察信号；
- 成功判定；
- 典型失败症状；
- 是否允许实现无关判定；
- 是否依赖 mock；
- 是否需要联动上游 / 下游 TU。

### 5.8.1 实现无关评测原则

对仓库级翻译而言，建议尽量采用“实现无关”而非“文本相似”的评测口径。

优先看：

- 是否编译通过；
- 是否满足接口 contract；
- 是否通过 hidden tests / mock tests；
- 是否在关键行为轨迹上等价；
- 是否遵守状态、线程和边界约束。

不应把“与参考答案语句相似”作为高优先级指标。

---

## 5.9 Pattern Memory 沉淀机制

`Pattern Memory` 的目标不是简单归档历史输出，而是把“可复用迁移模式”与“高价值失败模式”结构化沉淀下来。

它应当同时覆盖成功资产和失败资产。

### 5.9.1 成功模式应沉淀什么

建议每条成功模式至少包含：

- Pattern ID；
- 源侧模式名称；
- 目标侧模式名称；
- 适用前提；
- 禁用条件；
- 涉及边界；
- 推荐 TU 类型；
- 推荐 Skill；
- 推荐验证方式；
- 参考样例；
- 已验证证据；
- 常见误用。

例如可逐步沉淀的模式包括：

- `ArkTS Router → Cangjie Navigation Wrapper`
- `SignalKit reactive update → 仓颉响应式提交流水线`
- `Preferences API → 仓颉持久化适配层`
- `TDLib callback bridge → C-Interop 桥接骨架`

### 5.9.2 失败模式应沉淀什么

建议每条失败模式至少包含：

- Failure Pattern ID；
- 失败类型；
- 触发条件；
- 错误特征；
- 根因判断；
- 推荐补拉上下文；
- 推荐修复策略；
- 是否已被 Reviewer 规则覆盖；
- 是否已被 Repo Map 压缩规则覆盖；
- 是否已解决；
- 关联的 TU / 模块 / Skill / Trace。

这样做的目的是：

- 让同类错误不再反复以不同表象重现；
- 让 Repair 不只是“重写”，而是“调用已知修复套路”；
- 让 Repo Index / Repo Map 的缺陷也能被追踪和修正。

### 5.9.3 回写触发规则

建议在以下情况下回写 Pattern Memory：

- 某个 TU 经验证成功，且其迁移模式可复用；
- 某类错误重复出现两次以上；
- 同一问题在 Review 与 Verify 中均被捕获；
- 某次修复明显依赖新增上下文，说明现有闭包策略不足；
- 某次失败最终被确认为索引质量问题，而不是翻译质量问题。

### 5.9.4 Pattern Memory 与 Skill 的关系

二者不应混为一体。

- `Skill` 更偏“通用知识与系统约束”；
- `Pattern Memory` 更偏“本项目在真实流水线中验证过的迁移套路与失败套路”。

二者应该互相引用：

- Skill 可以引用经过验证的 Pattern；
- Pattern 可以标记依赖哪些 Skill；
- Failure Pattern 可以反向推动 Skill 补充“禁用条件”和“失败模型”。

## 6. 分阶段落地建议

本文是架构蓝图，不直接进入实现细节，但建议后续工作按以下顺序推进：

### 阶段一：先做 Repo Index 最小可用版

目标：

- 至少能稳定抽取文件、符号、导入导出、调用边、状态边界、线程边界；
- 能给 TelegramHarmony 输出第一版仓库快照；
- 能人工 spot check 结构质量。

### 阶段二：再做 Repo Map 三视图

目标：

- 稳定输出 `SQLite / JSONL / TXT` 三份产物；
- 可以按模块查看卡片；
- 可以按 TU 做最小闭包打包。

### 阶段三：定义 Translation Unit 和验证 oracle

目标：

- 针对 TelegramHarmony 的代表性模块做 TU 切分；
- 明确不同 TU 类型的强依赖与弱依赖；
- 明确首批 oracle 模板。

### 阶段四：把当前重试逻辑升级成四段编排

目标：

- Translate、Review、Verify、Repair 明确分工；
- 引入错误分类与错误驱动补拉；
- 不要求一开始就多供应商多模型。

### 阶段五：再开始中型模块试翻

目标：

- 选取状态、路由、长列表或互操作边界明显的模块；
- 先验证流水线设计，而不是追求覆盖率；
- 每轮运行都要产出 Pattern Memory 和 Failure Taxonomy。

## 7. 当前阶段明确不该做的事

为了避免设计与实现过早失焦，当前阶段明确不建议：

- 直接翻译 TelegramHarmony 全仓；
- 先做超重 GraphRAG 平台再开始验证；
- 仅构建向量检索，不构建符号 / 依赖索引；
- 让 Reviewer 只检查 Markdown 格式或 Schema 完整性；
- 在没有 TU 和 oracle 的情况下做大范围自动重试；
- 过早绑定双模型双供应商架构；
- 把所有失败都归因于模型，而不排查索引质量与闭包质量。

## 8. 与当前仓库资产的衔接建议

本文设计应与当前仓库已存在的资产协同，而不是重起炉灶。

### 8.1 与 Skill Schema V2 的衔接

`skills/SKILL_SCHEMA_V2.md` 已经明确：

- 架构映射；
- 边界契约；
- 执行拓扑；
- 状态契约；
- 失败模型；
- 验证矩阵。

这些字段可以直接成为：

- Repo Index 的风险标签参考；

- Pattern Memory 的结构化字段参考。

### 8.2 与当前样本与轨迹模板的衔接

现有样本记录和执行轨迹模板，应在后续扩展时补上：

- 对应 TU 类型；
- 对应 Repo Map 节点；
- 对应错误分类；
- 对应 Pattern Memory 条目。

这样可以避免样本、Skill、Trace、Pattern 四套资产互相断裂。

### 8.3 与当前脚本工具链的衔接

当前 `skill_generator_v2.py` 已经具备：

- 压缩 schema 骨架；
- 结构校验；
- 自动修复重试；
- 尝试过程落盘。

后续正式实现时，不建议推翻它，而是建议将其经验迁移到：

- TU Prompt 构造；
- Reviewer 契约检查；
- Verify 失败证据组织；
- Repair 的错误驱动重试。

## 9. 总结

对本项目而言，仓库级代码翻译真正需要先做的，不是“让模型一次读完整个仓库”，而是把仓库变成一套可索引、可压缩、可切分、可验证、可回写的中间层系统。

这套系统的关键不在于某个单一模型有多强，而在于以下五件事是否同时成立：

1. `Repo Index` 是否足够表达依赖、状态、线程和边界；
2. `Repo Map` 是否能在低 token 下保留关键约束；
3. `Translation Unit` 是否切得足够清晰且可验证；
4. `Translate → Review → Verify → Repair` 是否围绕证据而不是围绕主观判断运转；
5. `Pattern Memory` 是否让系统能从成功与失败中持续变聪明。

只有先把这五件事钉死，后续针对 TelegramHarmony 的中型模块试翻、复杂状态迁移、TDLib / C-Interop 边界验证，才不会建立在流沙之上。
