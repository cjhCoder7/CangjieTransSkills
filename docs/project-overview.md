# 项目概览

## 1. 项目背景

本项目围绕“将已有代码仓库翻译为仓颉语言版本”的目标展开，当前重点聚焦 Telegram 相关应用的真实模块级翻译验证，并以鸿蒙 / ArkTS 场景作为第一落点。当前默认阶段已进入 `Phase 03: Physical Iron Test`。

项目核心不是一次性完成代码翻译，而是建立一套可复用的：

- 文档整理方法；
- Skill 构建方法；
- 小样本验证流程；
- 翻译与运行验证闭环；
- 可追溯的实验与轨迹记录机制。

## 2. 核心目标

### 2.1 主目标

- 建立 `Agent + Skill` 驱动的仓颉代码翻译工作流；
- 构建鸿蒙应用开发 Skill 库；
- 先验证 `ArkTS → 仓颉`，再推进 Telegram ArkTS 工程翻译；
- 后续补齐 `Swift → 仓颉` 与 `Java/Python → 仓颉` 的转换验证。

### 2.2 交付目标

当前基于 `idea.md` 的交付理解如下：

- 至少覆盖三种源语言到仓颉语言的转换能力；
- Telegram 相关交付至少覆盖 ArkTS 与 Swift 两类源代码场景；
- 提供完整仓颉版本代码仓库或可复现产物；
- 保留转换过程轨迹、方法说明、验证结论；
- 通过单元测试与人工功能核查进行验收。

## 3. 当前范围

### 3.1 当前阶段纳入范围

- 官方文档与外部仓库调研；
- Skill 结构设计与最小单元定义；
- ArkTS 小样本筛选与翻译验证；
- 构建、运行、验证、记录流程设计；
- 仓库结构、文档基线与脚本骨架搭建。

### 3.2 当前阶段暂不纳入范围

- 直接翻译完整 Telegram 全量工程；
- 过早做大而全的自动化平台；
- 在未验证小样本闭环前扩展到太多语言；
- 把敏感密钥固化到仓库。

## 4. 当前硬性约束

- 需要 `DevEco Studio`；
- 需要仓颉插件才能开发仓颉鸿蒙应用；
- 当前部分文档和工具访问可能受审批权限限制；
- 任何技术结论都应尽量通过编译、测试、运行或实验记录来支撑。

## 5. 成功判断

当前阶段的“成功”可以按分层目标定义：

- 文档层：关键背景、资源、范围、约束已结构化；
- Skill 层：形成可复用的 Skill 模板或最小单元；
- 验证层：至少有一个 ArkTS 小样本跑通翻译与验证闭环；
- 工程层：目录、脚本入口、产物沉淀位置清晰；
- 交付层：后续 Agent 可以在当前仓库中直接继续推进而无需重新梳理项目背景。

## 6. 待确认事项

- Swift 目标源仓库；
- 第三语言最终选择 Java 还是 Python；
- 仓颉插件审批进度；
- 模型调用网关与正式环境变量约定；
- 轨迹信息记录格式与评测模板。
